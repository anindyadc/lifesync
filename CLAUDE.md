# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev       # Start Vite dev server
npm run build     # Production build to dist/
npm run lint      # ESLint (flat config, src/**/*.{js,jsx})
npm run preview   # Preview a production build locally
```

There is no test runner configured in this repo. Verify changes by running the app (`npm run dev`) and exercising the affected app module in the browser.

Local dev requires a `.env` file with `VITE_FIREBASE_*` keys (see `Readme.md` for the full list) pointing at a Firebase project with Authentication (Email/Password) and Firestore enabled.

## Architecture

LifeSync is a single-page React (Vite) app that hosts several independent "mini apps" behind one Firebase Auth + Firestore backend, gated by a per-user permission list.

### App shell and access control
- `src/App.jsx` is the shell: it listens to `onAuthStateChanged`, loads the user's profile document, and switches between mini apps via local `activeApp` state (no router — there's no routing dependency at all, view switching is plain state).
- User profiles live at `artifacts/default-app-id/public/data/userProfiles/{uid}` with `role` (`'user'` | `'admin'`) and `allowedApps` (array of app keys like `taskflow`, `walletwatch`). `isAllowed(appKey)` in `App.jsx`/`Sidebar.jsx` gates both the sidebar entry and the rendered component; admins bypass the check.
- `src/apps/admin/index.jsx` is the admin-only UI for toggling `role` and `allowedApps` on other users' profile docs.
- `src/components/Sidebar.jsx` and `App.jsx` duplicate the same nav/permission logic — when adding a new mini app, both files need the new case/button, plus `firestore.rules` and (if you want it enforced) `admin`'s `APPS_LIST`.

### Mini app module pattern
Each app under `src/apps/<name>/` is self-contained and follows the same shape:
- `index.jsx` — the app's root component, receives `user` as a prop, owns tab/view state.
- `hooks/use<Name>.js` — the only place that talks to Firestore for that app: sets up an `onSnapshot` listener scoped to `artifacts/default-app-id/users/{uid}/<collection>`, and exposes CRUD functions (`add*`, `update*`, `delete*`). Components never call Firestore directly.
- `components/` — presentational pieces specific to that app (forms, lists, charts, export/report views).
- Some apps have a second hook for exports, e.g. `hooks/useTaskExport.js`, `hooks/useExport.js` (CSV/PDF via `jspdf`/`jspdf-autotable`/`html2canvas`).

### Applications

- **TaskFlow** (`apps/taskflow`) — task manager with two task types: planned tasks (with subtasks) and a lightweight Quick List.
  - *Planned tasks*: subtasks, per-task/subtask time logs (add/delete only — delete and re-add to change a log), and progress that's manual unless subtasks exist, in which case it's auto-computed from subtask completion (the manual slider disables itself with an explanatory note). `hooks/useTasks.js` exports `getTaskMinutes(task)`, the single shared "time spent" definition (own + every subtask's `timeLogs`) used by the Dashboard, My Tasks, `TaskReportTable`, and export alike.
  - *Categories & Offices*: both user-editable, stored in one `settings/taskConfig` doc (`categories`/`offices` keys) via `hooks/useTasks.js`'s `add`/`removeCategory` and `add`/`removeOffice`; colors/icons come from `constants.js`'s `CATEGORICAL_PALETTE`/`CATEGORY_ICONS`. Each `id` intentionally equals the legacy plain-string value (e.g. `"General"`), not a slug, so pre-existing task docs keep matching without a migration. A tabbed "Manage Categories & Offices" modal in `index.jsx` shares one chip-list UI for both lists.
  - *Task Type*: `taskType` (`'personal'` | `'official'` — `constants.js`'s `TASK_TYPES`/`getTaskType`, defaulting missing/legacy values to `'personal'` so old tasks need no migration); official tasks add an `office` field pointing at the Offices list.
  - *Dashboard* (`DashboardStats.jsx` + `PriorityChart.jsx` + `CategoryChart.jsx`): month-navigable, 4-tile KPI row (with a MoM completion-rate delta), Priority/Category donuts (shared `SimpleDonutChart`), and the detailed report table (`TaskReportTable`, includes a Scope column). A View scope selector (All / Personal / Official (All Offices) / per-office) above the month nav filters the whole tab. `index.jsx`'s `getTasksForMonth` returns each in-scope task with its `subtasks` left as the FULL, unmodified list (so the Subtasks KPI and the Report table's progress column stay correct even for a subtask with no time logged that specific month) alongside a separate `monthlySubtasks` field — the same subtasks trimmed to just their monthly time logs — for whichever caller needs a month-scoped *time* total specifically (pass `{ timeLogs: task.timeLogs, subtasks: task.monthlySubtasks }` into `getTaskMinutes` rather than the task itself).
  - *My Tasks* (`components/TaskList.jsx`): search, priority/category/type/office filters, sort (due date or priority), bulk actions (multi-select → done/delete); Edit/Delete always reachable on mobile (previously a dead `MoreVertical` button hid them below `sm`). Card/List view toggle (`localStorage` key `taskflow-tasklist-view-mode`, defaults to card) — both share one `getTaskDerived()` computation plus `TaskBadges`/`SubtaskChecklist`, so only layout differs: `TaskCard`'s responsive grid vs. `TaskRow`'s `sm:grid-cols-[...]` row, sized so progress/badges scale with the row's actual width instead of a fixed `max-w` cap.
  - *Quick List* (`hooks/useQuickTasks.js` + `components/QuickList.jsx`): a separate, lighter same-day/tomorrow checklist (no subtasks/priority/category) in its own `quickTasks` collection. Each item's `forDate` ('YYYY-MM-DD') is fixed at creation; Overdue/Today/Tomorrow buckets are derived at render time by comparing to "now," so a "tomorrow" item auto-promotes on day rollover with no cron/migration. The header's (report-scoped) CSV/PDF export buttons are hidden on this tab.
  - *Report tab*: From/To date filtering (via `safeGetDate`, not raw `new Date(value)`, to avoid a UTC-parsing day-shift), its own independent Type/Office filters (consistent with the rest of the codebase's per-tab-filter convention rather than one shared global filter), and "Time by Office" / "Time by Category / Project" breakdown panels (summed from the same date-trimmed data as the per-task list, so totals reconcile). CSV/PDF export (`hooks/useTaskExport.js`) includes a Scope column (`Personal` / `Official` / `Official — <office>`).
- **WalletWatch** (`apps/walletwatch`) — expense tracker.
  - *Transactions*: amount is sign-normalized (`reimbursement` category forces positive, else negative), plus category, free-text tags, a Payment Mode (`constants.js`'s `PAYMENT_MODES` — UPI/Cash/Card/Bank Transfer, the last for NEFT/IMPS/net-banking/auto-debit that isn't a UPI push) + free-text Account, and a group/event label. A "settle" flow (`relatedTxn`) links a reimbursement entry back to the original expense and marks it `settled`.
  - *Categories*: user-editable, stored in `settings/walletConfig` (`constants.js` seeds defaults, assigning colors from `CATEGORICAL_PALETTE` by fixed creation-order slot, not a content hash); tag/group colors are deterministic via `getTagColor` (`lib/utils.js`). Two shared pure helpers live in `constants.js` (kept out of a component file so Fast Refresh doesn't choke on non-component exports): `isSettledSpend` (the app-wide definition of "spent" — personal, non-pending, non-official) and `getAccountKey` (an expense's free-text account, falling back to its Payment Mode label).
  - *Settings modal* (gear icon, `index.jsx`): besides Categories, has a "Data Cleanup" section that lists how many transactions are dated more than a year ago and, if any, offers to permanently delete them (batched `writeBatch` deletes, chunked at 450 docs to stay under Firestore's 500-op batch cap) behind the shared `ConfirmModal` — nothing is ever deleted automatically.
  - *Dashboard* (`DashboardStats.jsx` + `OverviewCharts.jsx`): 4-tile KPI row (spend, pending reimbursement, avg daily, txn count, MoM delta), then a "bento" grid rather than a fixed main/sidebar split — a top row pairs the two time-based visuals (`DailyCalendar` heatmap + `MonthlyTrendChart`, `lg:col-span-2`/`lg:col-span-3`), and every breakdown card (`CategoryBreakdown`, `WeeklyBarChart`, `PaymentModeBreakdown`, `PaymentAccountBreakdown`, `GroupSubtotals`, `OfficialTripsSummary`) flows into a responsive `1`/`2`/`3`-col grid below it. `PaymentAccountBreakdown` ("By Account") has a Month/Cycle toggle, plus, in Cycle mode, its own prev/next stepper (`cycleStep`, capped at `MAX_CYCLE_STEPS_BACK = 12`) independent of both the Month-mode toggle and the Dashboard's `selectedMonth` navigator: Month tallies `selectedMonth`; Cycle starts at today's cycle and steps back via `lib/cardCycles.js`'s `getCycleNStepsBack` (a thin `getPreviousCycle` wrapper for "N cycles ago," unlike `useCreditCards.cyclesForCard` below, which builds a full history list). Each account resolves its own window by looking itself up in the Cards tab's `cards` config by name — a match tallies against that card's real billing-cycle window (`getCycleForDate`) instead of the calendar month, so a card whose statement doesn't align to month boundaries (e.g. cycling on the 17th) still gets an accurate total, while an unmatched account is simply treated as `cycleStartDay = 1` so the same step-back loop covers Cash/plain-UPI too (this earlier shipped as two visually-similar side-by-side cards, "By Account" and "Account Tally"; merged into one toggle after user feedback that they looked redundant). A card-matched account in Cycle mode tallies Personal + Official spend, same as the Cards tab's real statement math (`useCreditCards.cyclesForCard`) — an unmatched account (Cash/plain UPI) stays Personal-only like the rest of this Dashboard, since there's no "statement" for it to agree with. Its drill-down modal adds a mini "By Category" / "By Payment Mode" split (segmented bar + legend, from that account's already-scoped `items`) above the flat transaction list. Each breakdown card already returns `null` when it has nothing to show for the month (e.g. no official trips) — since a `null` child renders no DOM node, the grid never reserves empty space for it, so the layout needs no separate "does the sidebar have anything to show" check. `DailyCalendar` itself is a GitHub-contribution-graph-style month grid (small `w-6`/`w-7` cells sharing one `inline-grid` instance with the weekday-letter header so the 7 columns stay pixel-aligned), heat-colored via RGB interpolation from indigo (low spend) to red (high spend), each cell showing its day-of-month number and opening a per-day drill-down (category breakdown + CSV/PDF export) on click.
  - *History tab* (`components/TransactionList.jsx`): groups by month/event/individual with progressive "Show More" disclosure; its own filter toolbar (free-text search, Category select, a Personal/Official scope pill filter on `isOfficial`, date range, multi-select Tags/Trips/Accounts via `MultiSelectFilter`, Payment Mode pills, sort by date/amount) and its own CSV/PDF export scoped to the current filter — the header's global export only renders on the Dashboard tab, since it's month-scoped and would otherwise silently export the wrong data while browsing History. Group headers show a Spent/Lent/Official split (via `isSettledSpend`), not a raw signed-amount sum. Row icons come from `CATEGORY_ICONS` (falling back to `DEFAULT_CATEGORY_ICON` for custom categories) plus a Payment Mode/Account badge.
  - *Card/List view toggle* (`localStorage` key `walletwatch-transactionlist-view-mode`, defaults to card, same pattern as TaskFlow's My Tasks toggle): a shared `renderTransactionItems(items)` helper switches between the `TransactionCard` grid and `TransactionRow` list for every grouping mode. `TransactionRow`'s list layout is a `sm:grid-cols-[...]` row — description | date+account (one line) | tags | amount | actions — sized to fill the row's actual width instead of stacking everything under the description.
  - *Add/Edit modal* (`components/TransactionForm.jsx`): sticky-header/scrollable-body/sticky-footer sheet; Trip/Tag/Account autocomplete suggestion buttons need `onMouseDown={(e) => e.preventDefault()}` (not just `onClick`), or the input's `onBlur` hides the list before the click registers (worse on mobile, where the closing keyboard adds to the race).
  - *Misc Expenses* (`components/MiscExpenseModal.jsx` + `hooks/useMiscExpenseDraft.js`, own header button, deliberately not a mode inside the main form): for small same-day spends (tea, auto, snacks, typically under ₹100) that are rarely all logged in one sitting, so the draft (label+amount items) persists in Firestore (`settings/miscExpenseDraft`), not local state — it survives closing/reopening the app later in the day, with a live count badge on the "Misc" button. "Save as Transaction" sums the draft into one expense (itemized description, e.g. `Tea (₹10), Auto (₹20)`) via the normal `handleSave` path, then clears the draft. Adds/saves only clear fields after the Firestore write resolves and surface the real thrown error on failure — an earlier optimistic-clear version masked failed writes (e.g. rules not yet deployed) as successes. Item IDs use a `generateId()` fallback since `crypto.randomUUID()` throws outside a secure context (plain `http://` LAN testing). Add/remove write via `arrayUnion`/`arrayRemove` rather than a read-modify-write of the whole `items` array, so two tabs/devices touching the draft near-simultaneously can't lose an item to a last-write-wins overwrite.
  - *Fixed Expenses* (`components/FixedExpenses.jsx` + `hooks/useFixedExpenses.js`, its own "Fixed" tab alongside Dashboard/History): recurring bills (rent, EMIs, subscriptions) defined once as a template (`fixedExpenseTemplates` collection — label, amount, category, a day-of-month due window `periodStartDay`–`periodEndDay`, active flag) that automatically produce a per-month "due" instance (`fixedExpenseInstances` collection) once the current month reaches `periodStartDay`. An unpaid instance is deliberately **not** a transaction — it's invisible to History/Dashboard totals/exports until the user hits "Mark Paid" (optionally adjusting amount/date/payment details, since bills like utilities vary from the template default), which writes a normal entry into `expenses` (tagged `isFixedExpense`/`fixedExpenseTemplateId`/`fixedExpenseInstanceId` for a "Fixed" badge in `TransactionList`) and flips the instance to `paid` — from that point it's indistinguishable from any other transaction. There's no Cloud Function/cron (this repo stays on the Spark plan — see the Telegram reminders section below for why that constraint exists); instance generation is a client-side check in `useFixedExpenses` that runs whenever the hook mounts, i.e. whenever WalletWatch is opened, so a bill becomes visible the next time the app loads on/after its due day rather than at the exact moment. An unpaid instance is never dropped across a month rollover — if it's still pending when the next month's window opens, both the carried-over and the new instance stay visible independently (you can owe two unpaid rents). `periodStartDay`/`periodEndDay` are clamped to the actual last day of the target month (`clampDayToMonth`, exported from `useFixedExpenses.js` and reused by the Credit Card Billing cycle math below) so a day-31 due date degrades gracefully in February. `DashboardStats.jsx`'s `FixedBillsDueCard` surfaces the selected month's pending/overdue instances (returns `null` when none, same convention as its sibling cards). Each template card also has a collapsible Payment History (matches past `expenses` by `fixedExpenseTemplateId`) so a bill's amount trend over time is visible, not just this month's status.
  - *Credit Card Billing* (`components/CreditCardBilling.jsx` + `hooks/useCreditCards.js` + `lib/cardCycles.js`, its own "Cards" tab): tallies cumulative spend on a credit card against its *actual statement cycle* rather than the calendar month. Each card (identified by the same free-text Account string — see `getAccountKey` above — matched across *both* Card- and UPI-mode transactions, since a UPI-linked credit card like a RuPay-on-UPI card is logged with `paymentMode: 'upi'` but is still a credit line with its own statement) is configured once in `settings/creditCardConfig` with a `cycleStartDay` (e.g. 5 → cycle runs the 5th through the 4th of the next month; day 1 degenerates to a plain calendar month, so an unconfigured card still works). `lib/cardCycles.js`'s `getCycleForDate`/`getPreviousCycle` resolve which cycle a date falls in and walk backward through cycle history. A cycle's spend is always computed live from `expenses` (never stored) — includes both Personal and Official card spend, since an actual statement doesn't care about that internal split, the whole thing still has to be paid. "Settle" records the bank payment that paid off a cycle (`cardCycleSettlements` collection — amount/date/payment source) and flags Settled/Short/Over based on the delta vs. computed spend; an unsettled cycle whose `cycleEnd` has already passed flags as Overdue instead (mirrors Fixed Expenses' overdue treatment). **Settling deliberately does not create an `expenses` doc** — each card purchase already counted as spend once when it was logged individually, so writing the lump-sum bank payment too would double it (it would need the same kind of exclusion `isSettledSpend` already gives pending reimbursements/Official spend, for no benefit); the settlement is visible only in the Cards tab, and History/Dashboard totals/exports are untouched by it. Each card also has a `cardType` (`'credit'`, default for legacy configs with no field, vs `'prepaid'`): prepaid cards are refilled a fixed amount by the company each cycle and never need reconciling against a bank payment, so `useCreditCards.cyclesForCard` skips the settlement lookup entirely for them. Instead of independent per-cycle math, a prepaid card's balance *rolls over*: a one-time `startingBalance`/`startingBalanceDate` (what the card had on it, as of some date — set in the Manage Cards modal, defaults to ₹0/today for a freshly-added card) anchors a forward walk (via `lib/cardCycles.js`'s `getNextCycle`) from that cycle up through the current one, applying `+ refillAmount` then `- cardSpend` per cycle so each cycle's closing balance becomes the next cycle's opening balance — matching how a real prepaid card actually behaves (unspent money doesn't reset each period). The UI shows a read-only On Budget/Overspent chip (with an Opening/Refill/Balance breakdown per cycle) and no Settle/Edit/Un-settle actions, since there's nothing to settle. Editing `startingBalance`/`startingBalanceDate` later re-walks the whole forward computation live (no stored per-cycle balance), so it doubles as a drift-correction tool if the tracked balance ever falls out of sync with the actual card.
- **ChangeManager** (`apps/changemanager`) — infrastructure change log with list, per-server timeline, and archive views; supports search/filter by server, application name, Status, and Type, CSV/PDF export of the filtered set, and archive/unarchive instead of hard delete for decluttering (hard delete is also available via a confirm modal). `hooks/useChanges.js` parses the form's `'YYYY-MM-DD'` date via `safeGetDate` (not raw `new Date(string)`) and only re-stamps a changed entry's time-of-day to "now" when the calendar day actually moved — otherwise it keeps the original time so editing an unrelated field doesn't reorder same-day entries in the date-sorted list/timeline.
  - *Dashboard* (list view): a bento row pairs `ActivityHeatmap` (`lg:col-span-2`, a GitHub-style month grid like WalletWatch's `DailyCalendar` but bucketed by change count, red-shifted on any day with a `failed` status rather than pure volume, click a day to set the header's date-range filter to that day) with `ChangeStatusChart`/`ChangeTypeChart` (`lg:col-span-3`, same `SimpleDonutChart` form as TaskFlow's Priority/Category charts, duplicated locally per the self-contained-module convention rather than cross-app imported). Below that, the list/card area (`lg:col-span-3`) sits next to a sidebar (`ServerFilter` + `ChangeStats`); `ChangeStats`' Failed Changes row is clickable and toggles the Status filter to `failed`.
  - *Card/List view toggle* (`localStorage` key `changemanager-changelist-view-mode`, defaults to card, same pattern as TaskFlow's My Tasks / WalletWatch's History toggle): switches between `ChangeCard`'s grid and `ChangeRow`'s `sm:grid-cols-[...]` row.
- **IncidentLogger** (`apps/incidentlogger`) — incident tracking with priority (`low`/`medium`/`high`/`critical`) and status (`open`/`resolved`), a dedicated "resolve" modal that stamps `resolvedBy`/`resolvedDate`, edit/delete of existing incidents, CSV/PDF export (`hooks/useIncidentExport.js`), and search by server/application combined with the status filter. `index.jsx` talks to Firestore directly (its own `onSnapshot`/`addDoc` calls) rather than through a hook, unlike other apps — this is intentional here (the previously-dead `hooks/useIncidents.js` was removed).
- **Investment** (`apps/investment`) — tracks holdings (holder, type, name, maturity date) with list, maturity-calendar (`FullCalendar`), search/filter by holder or type, a small stats summary (`components/InvestmentStats.jsx`), and CSV/PDF export; amounts are AES-encrypted client-side before being written (see notes below).
- **MediWatch** (`apps/mediwatch`) — prescription/medicine tracker with active/archived filtering plus search by patient/doctor/disease, multi-page photo capture (mobile camera or gallery upload, capped at 8 photos per prescription), per-medicine dosage/frequency/duration and optional alternate name, relative tagging (Self/Spouse/Father/Mother/Child/etc.), CSV/PDF export, and "smart archiving" that auto-archives prior active prescriptions for the same patient+doctor+disease (trimmed/case-insensitive match) when a new one is added (`archiveOld` flag in `addPrescription`).
- **Admin** (`apps/admin`) — table of all user profiles with inline toggles for `role` (admin/user) and per-app `allowedApps` checkboxes, search by name/email, and an explicit per-row Save (changes are local state until saved).

### Firestore data layout
All app data is namespaced under a single fixed `appId` (`'default-app-id'`, defined in `src/lib/firebase.js` and re-declared per-hook — not imported consistently, so check the local `APP_ID`/`appId` constant when editing a hook):
- `artifacts/{appId}/public/data/userProfiles/{uid}` — profiles/permissions (public-readable to any authenticated user, admin-writable).
- `artifacts/{appId}/users/{uid}/{collectionName}/{docId}` — per-user, per-app data, one collection per app (e.g. `tasks`, `expenses`, `prescriptions`).
- `artifacts/{appId}/users/{uid}/settings/walletConfig` — WalletWatch's single settings doc (category definitions).
- `artifacts/{appId}/users/{uid}/settings/miscExpenseDraft` — WalletWatch's in-progress Misc Expenses draft (cleared once saved as a transaction).
- `artifacts/{appId}/users/{uid}/settings/taskConfig` — TaskFlow's equivalent settings doc (custom category definitions), same shape/reasoning as WalletWatch's.
- `artifacts/{appId}/users/{uid}/quickTasks/{docId}` — TaskFlow's Quick List items.
- `artifacts/{appId}/users/{uid}/fixedExpenseTemplates/{docId}` / `.../fixedExpenseInstances/{docId}` — WalletWatch's recurring-bill definitions and their generated per-month due instances (see the Fixed Expenses bullet above).
- `artifacts/{appId}/users/{uid}/settings/creditCardConfig` — WalletWatch's credit card list + billing-cycle start days.
- `artifacts/{appId}/users/{uid}/cardCycleSettlements/{docId}` — WalletWatch's recorded bank payments per card billing cycle (see the Credit Card Billing bullet above).

`firestore.rules` is the authoritative security model (the copy embedded in `Readme.md` is an older/manual version — trust the actual `firestore.rules` file). It uses one generic rule keyed on the `{appName}` path segment plus `hasAppPermission(appName)`, so a new app collection is automatically covered as long as its Firestore path segment matches the `allowedApps` entry name — no rule changes needed unless the path shape differs, as WalletWatch's `settings/walletConfig`/`settings/miscExpenseDraft` and TaskFlow's `settings/taskConfig` do (each needs its own explicit rule block since the nested `settings/` path doesn't match the generic `{appName}/{docId}` shape). TaskFlow's `quickTasks` collection is a top-level (non-nested) collection but still needs its own explicit rule block, for a different reason: the generic rule's implicit permission check is keyed on the literal path segment (`hasAppPermission('quickTasks')`), which would wrongly require `'quickTasks' in allowedApps` instead of `'taskflow'`. ChangeManager's `changelogs` collection has the same mismatch (path segment `changelogs` vs. `allowedApps` key `changemanager`) and needs its own explicit rule block for the identical reason — this was missed for a while and silently denied non-admin users all ChangeLog access, so if you add a new app whose Firestore collection name doesn't literally equal its `allowedApps` key, add an explicit rule immediately rather than relying on the generic one. WalletWatch's `fixedExpenseTemplates`/`fixedExpenseInstances` and `cardCycleSettlements` collections have the identical mismatch (path segment vs. `walletwatch` allowedApps key) and each has its own explicit rule block for the same reason; `settings/creditCardConfig` needs its own block for the same nested-path reason as `settings/walletConfig`. MediWatch's `prescriptions` collection had this same mismatch (vs. the `mediwatch` allowedApps key) and was missed for a while — every non-admin grantee's reads/writes were silently denied — until an explicit rule block was added for it too; `admin/index.jsx`'s `APPS_LIST` also needs a matching `mediwatch` entry or admins have no UI toggle to grant it in the first place, which was the second half of that same gap. The `userProfiles` rule's `create` clause is intentionally narrower than "any owner" — it requires the exact `role: 'user'`/`allowedApps: []` shape the signup flow (`AuthScreen.jsx`) writes, closing a path where a user could otherwise call the Firestore SDK directly and self-grant `role: 'admin'`.

### Notable implementation details
- MediWatch stores prescription photos as compressed Base64 strings directly in Firestore documents (via `browser-image-compression`), not Firebase Storage — this was a deliberate choice to avoid Storage costs/config. A submit-time guard caps the total encoded payload well under Firestore's 1MiB document limit and the photo count at 8; `firebase/storage` is still used by `mediwatch`'s hook to delete Storage-backed URLs (legacy or removed-during-edit photos, filtered to exclude `data:` URIs first since those were never Storage objects), never Base64 ones. `useMedical.js` only ever *writes* the `photoUrls` array — it stopped also writing a redundant single `photoUrl` field (the first photo's full Base64 payload a second time, doubling that photo's cost against the 1MiB limit); `photoUrl` is still *read* as a fallback wherever a doc might predate the `photoUrls` array.
- Investment amounts are AES-encrypted client-side (`crypto-js`) before being written to Firestore (`amountEncrypted` field) and decrypted on read. The key comes from `VITE_INVESTMENT_SECRET_KEY` (see `Readme.md`'s env var list) — if unset, the hook falls back to an insecure placeholder and logs a console warning. Even configured, this is obfuscation against casual DB browsing, not real access control, since the key still ships in the client bundle. `decryptAmount` returns `null` (not `0`) when decryption fails or yields `NaN`, so UI code must handle a `null` amount as "undecryptable" distinctly from a real zero.
- Dates in Firestore are a mix of Firestore `Timestamp` and plain `'YYYY-MM-DD'` strings depending on the app/field; use the shared `safeGetDate` helper from `src/lib/utils.js` (Timestamp → `.toDate()`, `'YYYY-MM-DD'` string → local midnight, otherwise generic `new Date()`) instead of parsing dates ad hoc — a raw `new Date('YYYY-MM-DD')` parses as UTC and silently shows the wrong day for users east of UTC.
- Every app's CSV export (`useExport.js`/`useTaskExport.js`/`useChangeExport.js`/`useMedicalExport.js`/`useInvestmentExport.js`/`useIncidentExport.js`) has its own local `csvEscape`, duplicated per the self-contained-module convention rather than shared. Besides quoting commas/quotes/newlines, each one prefixes a value with a leading `'` if it starts with `=`, `+`, `-`, `@`, tab, or CR before quoting — otherwise a pasted description like `=HYPERLINK("http://evil","x")` executes as a formula when the exported file is later opened in Excel/Sheets (CSV/Excel formula injection, CWE-1236). Every column is escaped this way, not just the obviously free-text ones, since e.g. `formatAmount`'s locale-grouped commas or a custom category label can just as easily contain a comma or a leading special character.
- Shared UI primitives (`src/components/ui/`, `src/lib/utils.js`'s `cn`) follow the shadcn/Radix + `tailwind-merge`/`clsx` convention; prefer reusing `cn()` and existing `components/ui/*` over new one-off className logic. `src/components/ConfirmModal.jsx` is the standard confirm-dialog component (accessible: focus-trap-on-open, Escape-to-close, backdrop click, busy-guard against double-submit) — WalletWatch has its own visually-distinct local variant (`apps/walletwatch/components/ConfirmModal.jsx`) with the same accessibility behavior; Investment uses the Radix-based `components/AlertDialog.jsx` instead. Prefer the shared one for any new destructive-action confirmation.
- Path alias `@` → `src/` is configured in `vite.config.js`.
- `src/lib/firebase.js`'s `db` is created via `initializeFirestore(app, { localCache: persistentLocalCache(...) })`, not plain `getFirestore(app)` — every app's `onSnapshot` listeners get offline persistence (cached reads with no network, writes queue locally and flush on reconnect) for free. Falls back to `getFirestore(app)` if `initializeFirestore` throws (e.g. IndexedDB unavailable in some private-browsing modes), so a browser without persistence support still loads instead of crashing at startup.
- When a write needs to be idempotent against a possible duplicate trigger (e.g. WalletWatch's Fixed Expense instance generation and Credit Card cycle settlement, both of which can be triggered from multiple tabs/devices near-simultaneously), prefer `setDoc(doc(col, deterministicId), ...)` over `addDoc` + an existing-doc query — the query-then-write pattern has a race window between the check and the write that a deterministic ID closes entirely, since a second write just overwrites the same doc instead of creating a duplicate.

### TaskFlow Telegram reminders (`scripts/task-reminders/` + `.github/workflows/task-reminders.yml`)
Reminder-only (no "mark done" webhook — deliberately scrapped to avoid needing any public HTTP endpoint or a paid Firebase plan). Runs entirely on GitHub Actions' free scheduled workflows, reusing infra this repo already has (`deploy.yml`) rather than adding a new hosting account: `task-reminders.yml` fires daily (`cron: '30 2 * * *'`, i.e. 08:00 IST) plus `workflow_dispatch` for manual testing, and runs `scripts/task-reminders/send-reminders.js` — a standalone Node script (its own `package.json`, isolated from the Vite app's dependencies) that authenticates to Firestore with a downloaded service-account key (`admin.credential.cert(...)`, not `firebase-admin`'s default ambient credentials) and stays entirely on the free Spark plan since it never touches Cloud Functions. It queries the single configured user's `tasks` collection, finds anything `status !== 'done'` with `dueDate` today or earlier, and sends one plain Telegram message listing them (oldest-overdue first) via the Bot API — nothing is sent when there's nothing pending. Secrets (`FIREBASE_SERVICE_ACCOUNT` — the full downloaded JSON key, `TARGET_UID`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`) live in the GitHub repo's Actions secrets, never committed.

## Deployment

- Deploys to GitHub Pages via `.github/workflows/deploy.yml` on every push to `main` (no staging branch/environment currently). Firebase env vars are injected from GitHub Actions secrets at build time.
- `vite.config.js`'s `base: '/lifesync/'` must match the GitHub repo name — if the repo is renamed or forked, update this first or the deployed app 404s on assets.
- Version bumps use `npm version <major|minor|patch> -m "chore(release): %s"`; commit messages follow Conventional Commits (`feat:`, `fix:`, `chore:`).
